OpenAI's Codex team published two foundational articles on harness engineering in early 2026, documenting their experience building a real product with zero hand-written code. Their approach represents the most extreme test of agent-first development: approximately 1 million lines of code, 1,500 merged PRs, initially 3 engineers (later 7), with every line written by Codex agents. The team estimates they built in about 1/10th the time it would have taken to write the code by hand. [Source: raw/openai-com-index-harness-engineering.md]

## The Experiment: Zero Hand-Written Code

Starting from an empty git repository in late August 2025, a small team at OpenAI built and shipped an internal product with external alpha testers. The constraint was intentional: "no manually-written code." The initial scaffold -- repository structure, CI configuration, formatting rules, package manager setup, application framework, and even the initial AGENTS.md -- was itself generated by Codex CLI using GPT-5. [Source: raw/openai-com-index-harness-engineering.md]

Key metrics:
- ~1 million lines of code across application logic, infrastructure, tooling, documentation, and internal developer utilities
- 1,500 pull requests opened and merged in 5 months
- 3.5 PRs per engineer per day average
- Throughput *increased* as the team grew from 3 to 7 engineers
- Single Codex runs regularly worked for 6+ hours on a single task
- The product has been used by hundreds of users internally, including daily power users

[Source: raw/openai-com-index-harness-engineering.md]

## Redefining the Engineer's Role

When humans stop writing code, the job shifts to: "design environments, specify intent, and build feedback loops that allow Codex agents to do reliable work." Early progress was slower than expected, not because Codex was incapable, but because the environment was underspecified. The agent lacked the tools, abstractions, and internal structure required to make progress toward high-level goals. [Source: raw/openai-com-index-harness-engineering.md]

The primary engineering question became: **"What capability is missing, and how do we make it both legible and enforceable for the agent?"** When something failed, the fix was almost never "try harder." Engineers stepped into the task and identified what capability was missing. [Source: raw/openai-com-index-harness-engineering.md]

Human interaction is almost entirely through prompts. Engineers describe tasks, run agents, and allow them to open PRs. To drive a PR to completion, Codex is instructed to review its own changes locally, request additional specific agent reviews, respond to feedback, and iterate in a loop until all agent reviewers are satisfied (effectively a Ralph Wiggum Loop). Review is increasingly agent-to-agent -- humans may review PRs but are not required to. [Source: raw/openai-com-index-harness-engineering.md]

## AGENTS.md as Table of Contents, Not Encyclopedia

The team tried "one big AGENTS.md" and it failed for four reasons: [Source: raw/openai-com-index-harness-engineering.md]

1. **Context is scarce** -- a giant instruction file crowds out the task, the code, and relevant docs. The agent either misses key constraints or starts optimizing for the wrong ones.
2. **Too much guidance becomes non-guidance** -- when everything is "important," nothing is. Agents end up pattern-matching locally instead of navigating intentionally.
3. **It rots instantly** -- a monolithic manual becomes a graveyard of stale rules. Agents cannot tell what is still true, humans stop maintaining it.
4. **It's hard to verify** -- a single blob does not lend itself to mechanical checks (coverage, freshness, ownership, cross-links), so drift is inevitable.

Instead, they treat AGENTS.md as a ~100-line **table of contents** pointing to a structured `docs/` directory: [Source: raw/openai-com-index-harness-engineering.md]

```
AGENTS.md          (~100 lines, map with pointers)
ARCHITECTURE.md
docs/
  design-docs/   (indexed, verified, including core-beliefs.md)
  exec-plans/    (active/, completed/, tech-debt-tracker.md)
  generated/     (db-schema.md, auto-generated)
  product-specs/ (indexed)
  references/    (*.llms.txt files)
  DESIGN.md
  FRONTEND.md
  PLANS.md
  PRODUCT_SENSE.md
  QUALITY_SCORE.md
  RELIABILITY.md
  SECURITY.md
```

This enables **progressive disclosure**: agents start with a small, stable entry point and are taught where to look next, rather than being overwhelmed up front. Plans are treated as first-class artifacts -- ephemeral lightweight plans for small changes, execution plans with progress and decision logs checked into the repository for complex work. [Source: raw/openai-com-index-harness-engineering.md]

The knowledge base is enforced mechanically. Dedicated linters and CI jobs validate that it is up to date, cross-linked, and structured correctly. A recurring "doc-gardening" agent scans for stale or obsolete documentation and opens fix-up pull requests. [Source: raw/openai-com-index-harness-engineering.md]

## Agent Legibility as the Primary Goal

Because the repository is entirely agent-generated, it is optimized for **agent legibility** first. The key insight: from the agent's point of view, anything it cannot access in-context while running effectively does not exist. [Source: raw/openai-com-index-harness-engineering.md]

- Knowledge that lives in Google Docs, chat threads, or people's heads is invisible to the system. That Slack discussion that aligned the team on an architectural pattern? If it is not discoverable to the agent, it is illegible. [Source: raw/openai-com-index-harness-engineering.md]
- Repository-local, versioned artifacts (code, markdown, schemas, executable plans) are the only truth. [Source: raw/openai-com-index-harness-engineering.md]
- They favor "boring" technologies that are composable, API-stable, and well-represented in training data. Technologies described as "boring" tend to be easier for agents to model. [Source: raw/openai-com-index-harness-engineering.md]
- Sometimes it is cheaper to have the agent reimplement functionality than to work around opaque upstream behavior from public libraries. Example: rather than pulling in a generic p-limit-style package, they implemented their own map-with-concurrency helper integrated with OpenTelemetry instrumentation, with 100% test coverage. [Source: raw/openai-com-index-harness-engineering.md]

Pulling more of the system into a form the agent can inspect, validate, and modify directly increases leverage -- not just for Codex, but for other agents (e.g., Aardvark) working on the codebase. [Source: raw/openai-com-index-harness-engineering.md]

## Enforcing Architecture and Taste Mechanically

Agents are most effective in environments with **strict boundaries and predictable structure**. The team built around a rigid architectural model: [Source: raw/openai-com-index-harness-engineering.md]

- Each business domain is divided into fixed layers (Types -> Config -> Repo -> Service -> Runtime -> UI). Code can only depend "forward" through these layers.
- Cross-cutting concerns (auth, connectors, telemetry, feature flags) enter through a single explicit interface: Providers. Anything else is disallowed.
- Dependency directions are strictly validated.
- Custom linters and structural tests enforce constraints mechanically. Linters are Codex-generated.
- Lint error messages are written as remediation instructions injected into agent context.

[Source: raw/openai-com-index-harness-engineering.md]

"Taste invariants" enforce structured logging, naming conventions, file size limits, and platform-specific requirements. When documentation falls short, rules are promoted into code. Human taste is fed back continuously: review comments, refactoring PRs, and user-facing bugs are captured as documentation updates or encoded directly into tooling. [Source: raw/openai-com-index-harness-engineering.md]

The philosophy: enforce boundaries centrally, allow autonomy locally. You care deeply about boundaries, correctness, and reproducibility. Within those boundaries, you allow agents significant freedom in how solutions are expressed. The resulting code does not always match human stylistic preferences, and that is acceptable. As long as the output is correct, maintainable, and legible to future agent runs, it meets the bar. [Source: raw/openai-com-index-harness-engineering.md]

## Garbage Collection of AI Slop

Full agent autonomy introduces entropy. Codex replicates patterns that already exist -- even suboptimal ones. The team initially spent every Friday (20% of the week) cleaning up "AI slop." That did not scale. [Source: raw/openai-com-index-harness-engineering.md]

Instead, they encoded "golden principles" into the repository and built recurring cleanup processes: [Source: raw/openai-com-index-harness-engineering.md]

- Background Codex tasks scan for deviations from golden principles on a regular cadence.
- Quality grades are updated automatically.
- Targeted refactoring PRs are opened (most reviewable in under a minute, automerged).
- Examples of golden principles: prefer shared utility packages over hand-rolled helpers (keeps invariants centralized); do not probe data "YOLO-style" -- validate boundaries or rely on typed SDKs.
- "Technical debt is like a high-interest loan: it's almost always better to pay it down continuously in small increments than to let it compound."

Human taste is captured once, then enforced continuously on every line of code. This catches and resolves bad patterns on a daily basis, rather than letting them spread for days or weeks. [Source: raw/openai-com-index-harness-engineering.md]

## Application Legibility

As throughput increased, the bottleneck became human QA capacity. The team made the application itself legible to Codex: [Source: raw/openai-com-index-harness-engineering.md]

- The app is bootable per git worktree, so Codex could launch and drive one instance per change.
- Chrome DevTools Protocol wired into the agent runtime. Skills created for working with DOM snapshots, screenshots, and navigation. Codex could reproduce bugs, validate fixes, and reason about UI behavior.
- Observability tooling: logs, metrics, and traces exposed via a local observability stack ephemeral for any given worktree. Agents can query logs with LogQL and metrics with PromQL.
- Prompts like "ensure service startup completes in under 800ms" or "no span in these four critical user journeys exceeds two seconds" become tractable.

[Source: raw/openai-com-index-harness-engineering.md]

## The Codex App Server

The second article (Celia Chen, February 4, 2026) describes the Codex App Server, the unified backend that powers all Codex surfaces (web app, CLI, IDE extension, macOS app). It is the "critical link" between the shared Codex harness (agent loop + logic) and the various client experiences. [Source: raw/openai-com-index-unlocking-the-codex-harness.md]

### Architecture

All agent logic lives in "Codex core" -- both a library and a runtime that manages one Codex thread (conversation). The App Server is a long-lived process that hosts Codex core threads and exposes them via a bidirectional JSON-RPC protocol (a "JSON-RPC lite" variant: keeps request/response/notification shape, omits the "jsonrpc": "2.0" header, framed as JSONL over stdio). [Source: raw/openai-com-index-unlocking-the-codex-harness.md]

Components: stdio reader, Codex message processor, thread manager, and core threads. The thread manager spins up one core session per thread. The message processor translates client JSON-RPC requests into Codex core operations and transforms low-level events into stable, UI-ready JSON-RPC notifications. [Source: raw/openai-com-index-unlocking-the-codex-harness.md]

### Conversation Primitives

Three core primitives: [Source: raw/openai-com-index-unlocking-the-codex-harness.md]

1. **Item**: The atomic unit of input/output. Typed (user message, agent message, tool execution, approval request, diff). Explicit lifecycle: item/started, optional item/*/delta events, item/completed.
2. **Turn**: One unit of agent work initiated by user input. Contains a sequence of items.
3. **Thread**: The durable container for an ongoing session. Can be created, resumed, forked, archived. History is persisted.

The server can initiate requests when the agent needs input (like an approval), pausing the turn until the client responds. [Source: raw/openai-com-index-unlocking-the-codex-harness.md]

### Client Integration Patterns

Three patterns for embedding Codex: [Source: raw/openai-com-index-unlocking-the-codex-harness.md]

- **Local Apps & IDEs**: Bundle a platform-specific App Server binary, launch as long-running child process, bidirectional stdio channel. Some partners decouple release cycles by pointing to newer App Server binaries without waiting for client releases.
- **Codex Web**: Container environment. Worker provisions container with workspace, launches App Server inside, maintains JSON-RPC over stdio. Web app talks to Codex backend over HTTP and SSE. Browser-side UI stays lightweight; state lives on the server so work continues if the tab disappears.
- **TUI/Codex CLI**: Historically ran in the same process. Being refactored to use App Server as any other client, enabling connection to remote Codex servers.

Client bindings have been implemented in Go, Python, TypeScript, Swift, and Kotlin. TypeScript definitions can be generated directly from the Rust protocol. [Source: raw/openai-com-index-unlocking-the-codex-harness.md]

## Increasing Levels of Autonomy

At full maturity, given a single prompt, Codex can: [Source: raw/openai-com-index-harness-engineering.md]

1. Validate the current state of the codebase
2. Reproduce a reported bug
3. Record a video demonstrating the failure
4. Implement a fix
5. Validate the fix by driving the application
6. Record a second video demonstrating the resolution
7. Open a pull request
8. Respond to agent and human feedback
9. Detect and remediate build failures
10. Escalate to a human only when judgment is required
11. Merge the change

This depends on specific repository structure and tooling and should not be assumed to generalize without similar investment. [Source: raw/openai-com-index-harness-engineering.md]

## Key Lessons

1. **Map, not manual** -- AGENTS.md should be ~100 lines pointing to deeper sources, not a monolithic instruction set. [Source: raw/openai-com-index-harness-engineering.md]
2. **Agent legibility > human aesthetics** -- code does not have to match human style preferences as long as it is correct, maintainable, and legible to future agent runs. [Source: raw/openai-com-index-harness-engineering.md]
3. **Enforce boundaries centrally, allow autonomy locally** -- like leading a large platform engineering organization. [Source: raw/openai-com-index-harness-engineering.md]
4. **Encode taste mechanically** -- human taste is captured once, then enforced continuously on every line of code via linters, structural tests, and recurring cleanup agents. [Source: raw/openai-com-index-harness-engineering.md]
5. **Garbage-collect continuously** -- do not let AI slop compound; pay down technical debt in small increments daily. [Source: raw/openai-com-index-harness-engineering.md]
6. **Make everything legible to the agent** -- logs, metrics, traces, UI state exposed via tools so performance and behavioral prompts become tractable. [Source: raw/openai-com-index-harness-engineering.md]
7. **Throughput changes the merge philosophy** -- minimal blocking merge gates, short-lived PRs, test flakes addressed with follow-up runs. Corrections are cheap, waiting is expensive. [Source: raw/openai-com-index-harness-engineering.md]
